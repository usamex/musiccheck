**M4. The stored catalog file can become permanently truncated.** CONFIRMED by code.
- Where: `catalog.py:152-153`.
- What: `if not final_path.exists(): shutil.copyfile(...)` is not atomic. A crash or disk-full mid-copy, or two concurrent identical ingests (the second truncates and rewrites the first's file), can leave a partial file. Every later ingest of the same sha skips the copy, so the row points at a broken reference forever.

**M5. Deleting a track can leave stale vectors in the provider index.** PLAUSIBLE: it shows up once a persistent-index provider exists.

### One deviation from the brief you need to know about
The upload does **not** send `{uri, name: 'query.m4a', type: 'audio/mp4'}`, because that breaks in SDK 58:
- On iOS and Android the global `fetch` is now `expo/fetch`. The SDK 58 docs say so, and the code is in `node_modules/expo/src/winter/runtime.native.ts`.
- Its multipart encoder rejects RN's `{uri,…}` FormData parts with "Unsupported FormDataPart implementation". Expo's own test `convertFormData-test.native.ts` asserts this.
- The app would have reported every upload as a network error.

What the client does instead:
- It appends an expo-file-system `File`, which is the SDK 58 documented way.
- The multipart filename is therefore the recording's own name: `recording-<uuid>.m4a` on iOS, `<uuid>.m4a` on Android. The backend only uses the suffix (`uploads.py:safe_suffix`) and probes the content with FFmpeg, so the contract still holds.
- `expo/fetch` throws `FetchError`, not `TypeError`, on network failure. So any fetch rejection that isn't an abort maps to `network_unavailable`.

### expo-audio 58.0.9 facts I confirmed
Checked in the installed `.d.ts` files and the native Kotlin/Swift sources, plus the v58 docs:
- **Recorder:** `useAudioRecorder(options, statusListener?)` returns an `AudioRecorder` that is released on unmount. You call `prepareToRecordAsync()`, then `record()` (synchronous), then `await stop()`, then read `recorder.uri`.
  - On Android `uri` is `""` when there is no file, and it keeps the last path after `stop()`.
  - On iOS each prepare creates a new file under `Caches/ExpoAudio/recording-<UUID>.m4a`.
  - On Android, preparing twice throws `AudioRecorderAlreadyPreparedException`.
- **Permissions:** `getRecordingPermissionsAsync()` and `requestRecordingPermissionsAsync()` return `{granted, status, canAskAgain, expires}`.
- **Audio mode:** `setAudioModeAsync(Partial<AudioMode>)`. On iOS `allowsRecording: true` is required, otherwise `record()` throws "Recording not allowed". `playsInSilentMode` defaults to true; `interruptionMode` defaults to `mixWithOthers`.
- **Presets:** `RecordingPresets.HIGH_QUALITY` is **stereo**, so I set every option explicitly.
  - Shared: `.m4a`, 44100 Hz, mono, 128 kbps, cache directory.
  - Android: `outputFormat 'mpeg4'`, `audioEncoder 'aac'`, `audioSource 'mic'` (also the native default).
  - iOS: `IOSOutputFormat.MPEG4AAC`, `AudioQuality.MAX`.
- **Config plugin:** `microphonePermission` and `recordAudioAndroid` set; background recording and playback disabled. `expo config --type introspect` shows the iOS `NSMicrophoneUsageDescription` and Android `RECORD_AUDIO` are present.
